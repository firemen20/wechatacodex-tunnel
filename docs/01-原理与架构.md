# 原理与架构

## 一、节点到底在哪里

```
你的手机/电脑 ──▶ Cloudflare 边缘节点（就近接入）──▶ Worker ──▶ 目标网站
                  ↑
            你配置里的 server（IP 或域名）
```

关键认知：**Worker 是代码，运行在 Cloudflare 全球网络上**。客户端连接的其实是**离你最近的 CF 边缘节点**，由边缘节点转发到执行 Worker 的那台机器。

所以配置里的 `server` 填哪个 IP，就决定了你连哪个边缘 —— **不同边缘质量差别很大**，这就是要「优选 IP」的原因。

---

## 二、`*.workers.dev` 为什么不能用

`<worker>.<子域>.workers.dev` 是 Cloudflare 分配的默认域名，在国内有双重封锁：

| 封锁手段 | 现象 |
|---|---|
| **DNS 污染** | 解析返回假 IP（非 CF 段），连上去是个无关的服务器 |
| **SNI 阻断** | TLS 握手中带 `workers.dev` 的 SNI，连接被重置 |

### 两条出路

**① 裸 IP + 明文端口**

```
server: 172.66.0.1        ← 直接写 CF 边缘 IP，不过 DNS
port:   2052              ← CF 接受明文 HTTP 的端口
tls:    false             ← 不加密 → 没有 SNI → 不会被 SNI 阻断
ws-opts:
  headers:
    Host: <worker>.workers.dev   ← 用 Host 头告诉 CF 要访问哪个 Worker
```

优点：不需要域名，任何客户端都支持。
缺点：手机→CF 边缘这一段不加密（访问 HTTPS 网站时，端到端内容仍是 TLS）。

**② 自定义域名 + TLS 443**（推荐）

把域名托管到 Cloudflare，给 Worker 绑一个自定义域名。**自定义域名没被墙**，所以能正常用 TLS 443。

```
server:     172.66.0.1          ← 仍然用裸 IP，避开 DNS 污染
port:       443
tls:        true
servername: node1.example.com   ← SNI 用自定义域名（未被阻断）
ws-opts:
  headers:
    Host: node1.example.com
```

优点：全链路加密、更稳定、五种客户端全支持。
前提：需要一个域名，且必须是 CF 能接受的 **zone**（见 `docs/02-自定义域名.md`）。

## 三、反代IP（PROXYIP）—— 第二层依赖

代码里有个「反代IP」概念，很容易被忽略。

### 它解决什么问题

当**目标网站自己也托管在 Cloudflare 上**时（Discord、知乎、Medium……），Worker 直连它会**回环**，所以要绕一个中转 IP。

### 什么时候用

worker 的建连逻辑是：

```
① 先试直连  connectDirect(host, port)
② 直连失败 → 才走反代  connecttoPry()
```

所以：

| 网站类型 | 走反代吗 |
|---|---|
| 普通网站（大多数） | ❌ 不走 |
| **CF 托管网站** | ✅ 走 |

**反代IP 挂了只会影响 CF 托管的那批网站，普通网站不受影响。**

### 配置

Worker 环境变量 `PROXYIP`。实测对比（A=固定 `proxyip.cmliussss.net` / B=不设，走代码默认的按机房就近）：

| 站点 | A 固定 | B 默认 |
|---|---|---|
| cloudflare.com | **0.90s** | 1.58s |
| discord.com | **0.60s** | 0.72s |
| 总体中位 | **0.69s** | 0.76s |

> **结论：固定值不差，甚至更快。不要盲目"改回默认"。**
> 推测原因：固定值指向的后端可能是专门为国内线路调优的。
> 但这个结论与网络环境有关，**建议你在自己的环境里实测后再决定**。

## 四、优选 IP 为什么要"实测反选"

### 问题：扫描排名不可靠

最早的做法是「扫一遍候选 IP → 按扫描结果取前几名」。实测发现这会把配置**越维护越差**：

```
维护前：中位 920ms，最快 381ms
维护后：中位 1006ms，最慢 3406ms，还挂了 1 个节点
```

原因是扫描阶段是**单次测量**，噪声极大。

### 解法：三步改进

1. **所有候选全测**，不只测扫描前几名
2. **把上一轮在用的 IP 并进候选** —— 否则好 IP 会被白白丢掉
3. **双轮复验** —— 最终配置再测一遍，**两轮都通过**的节点才保留

实测效果：同一份代码，改进后选出的 IP 稳定在 660ms~1.7s，不再出现随机劣化。

## 五、数据流

```
config.json
    │
    ├─▶ tools/optimize-ips.js
    │     ├─ 扫描候选 IP（工具：verify-config.js）
    │     ├─ 实测反选最优 N 个
    │     ├─ 生成配置（工具：build-nodes.js）
    │     ├─ 双轮复验
    │     └─ 生成各客户端格式（工具：build-subscription.js）
    │
    └─▶ dist/
          ├─ ClashMeta-FlClash.yaml
          ├─ 通用订阅-base64.txt
          ├─ Hiddify-Nekoray-singbox.json
          └─ 节点链接.txt
```

每个环节都可以单独跑，方便调试。
